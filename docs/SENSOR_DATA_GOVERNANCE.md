# Sensor Data Governance

This document defines the governance model for sensor data in the public ESP32 IoT Security Governance Lab.

The current firmware uses synthetic local sensor simulation only. It does not read a real sensor, transmit data or store customer-specific measurements.

## Purpose

Sensor data must be governed because it can reveal operational, environmental or usage patterns in real projects.

For this public lab, the goal is to show how sensor data handling can be documented without exposing real project data.

## Current implementation

The current implementation includes:

- `include/sensor_simulation.h`
- `src/main.cpp`

The firmware generates synthetic temperature and humidity values and prints them to the serial console as part of the local status output.

## Data classification

Current public lab data classification:

| Data item | Classification | Notes |
| --- | --- | --- |
| Sensor sequence | Synthetic | Local counter only |
| Temperature value | Synthetic | Generated by deterministic demo logic |
| Humidity value | Synthetic | Generated by deterministic demo logic |
| Device id | Synthetic | Example value only |
| Site label | Synthetic | Example value only |

## Public repository rule

The public repository may contain only synthetic sensor data and synthetic examples.

Do not commit:

- Real sensor logs.
- Real environmental measurements from customer locations.
- Real operational telemetry.
- Real customer identifiers.
- Real device inventory.
- Real site labels.
- Exported logs from protected environments.

## Telemetry boundary

Current baseline:

- Sensor simulation: enabled locally.
- Serial output: enabled locally.
- Network transmission: disabled.
- Telemetry upload: disabled.
- OTA: disabled.

Any change that sends sensor data outside the device must be treated as a governed change.

## Governed change triggers

A sensor-data change requires review when it affects:

- Real sensor integration.
- Data retention.
- Network transmission.
- Telemetry content.
- Sampling interval.
- Device identity linkage.
- Location or site labels.
- Customer-specific operational context.

## Minimum evidence for real sensor use

Before real sensor use, document:

- Sensor type.
- Purpose of measurement.
- Data classification.
- Sampling interval.
- Local retention behavior.
- Transmission behavior.
- Access control model.
- Deletion or retention policy.
- Rollback plan.
- Validation evidence.

## Principle

Sensor data should be treated as potentially sensitive until classified otherwise.

The public lab uses synthetic local-only values to demonstrate governance without exposing real-world data.
